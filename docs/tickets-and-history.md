# Тикеты, MCP и история

Развёртывание с нуля: [setup.md](setup.md), разделы 1–5.
DDL — src/ydb_tickets/schema.sql, контракты MCP — src/ydb_tickets/mcp-tools.yaml.

## Инструменты

Функция ydb-tickets принимает прямой JSON или HTTP body. create-ticket требует
user_id, category и text; list-my-tickets — user_id. Без action наличие text/category
означает создание. Допустимые категории: bug, docs, feature, access.
user_id проверяется как email и нормализуется. Guardrail повторно проверяет текст
при создании; PII маскируется на границе записи. Опасные просьбы запрещены,
даже если оформлены как заявка или приказ владельца.

Поллер предоставляет модели create-ticket только как предложение аргументов
с require_approval=always. Он не передаёт модельному API разрешение на запись.
После ответа поллер выбирает первое предложение, проверяет category/text и защиту,
подставляет адрес реального отправителя и стабильный request_id письма и выполняет
ровно один MCP tools/call через SDK. Остальные предложения не выполняются.
У list-my-tickets остаётся require_approval=never, поскольку это чтение.

## Идемпотентность

request_id — UUID входящей реплики, полученный из ящика, UIDVALIDITY и UID письма.
В функции тикетов request_id вместе с user_id определяет UUID тикета. Условная
запись и чтение выполняются в одной SerializableReadWrite-транзакции YDB.
Повтор возвращает исходную строку, не меняя её текст, дату или escalated-статус.
Новая таблица не требуется. Прямое ручное создание без request_id совместимо
со старым API, но намеренно не имеет гарантии повторного использования тикета.

## История

messages хранит role, текст, модель, tokens_in/tokens_out, latency_ms и ticket_id.
Последние десять реплик читаются в JSON-архив контекста для операций с тикетами.
Поиск по базе изолирован: получает текущее обращение и только file_search, без
старых ответов и MCP. Для явных ссылок вроде «как это исправить» допустим только
предыдущий пользовательский вопрос. Перед вызовом сохраняется
входящая реплика; после вызова — ответ с реальным usage модели. Две реплики цикла
создания связываются с одним возвращённым ticket_id. Время включает модель и
контролируемый MCP-вызов. Прямой контроллерный трейс записывается отдельно от
output[] Responses API; model usage относится только к генерации.

## Проверка

```bash
python -m unittest discover -s tests -v
python scripts/check_qa_flow.py
yc serverless function invoke ydb-tickets \
  --data '{"action":"list-my-tickets","user_id":"<ваш-email>"}'
```

Облачный QA проверяет RAG, один контролируемый вызов создания, повтор с тем же
request_id, одну запись tickets, четыре messages, две связи и точность метрик.
SMTP подменён, случайные тестовые строки удаляются. Деплой функции и MCP-контракта
должен предшествовать запуску проверки новой версии.

From не подтверждает личность; отдельного ACL сотрудников нет. Классификатор
и согласие не заменяют авторизацию. SMTP и запись YDB не образуют общей транзакции.
