# Защита и персональные данные

## Trusted и untrusted

Trusted: системный промпт, код, определения инструментов, параметризованные YQL,
константная задача и примеры классификатора. Untrusted: письмо, From, архив
переписки, RAG-фрагменты и аргументы модели. Внешний текст не попадает в instructions.
Архив conversation_history передаётся внутри JSON для маршрутов тикетов;
поисковый маршрут изолирован от старых ответов и MCP.
From служит идентификатором канала, но не подтверждает личность сотрудника.

## Проверки перед действием

1. Unicode-нормализация и regex блокируют подмену инструкций, разрушительные SQL
   и просьбы удалить/очистить таблицы, базу либо тикеты, отключить защиту.
   Приказ владельца или оформление опасного действия как заявки не разрешает его.
2. Остальной текст после маскирования проверяет few-shot Text Classification API:
   safe / injection / off-topic. Задача и примеры фиксированы, обращение идёт отдельно.
3. Поллер отказывает на injection без предложения тикета, off-topic ограничивает
   рамками Help Desk. Для короткого согласия сначала проверяется исходная просьба,
   в том числе после старого ошибочного предложения агента.
4. Функция ydb-tickets независимо проверяет текст перед записью. Injection возвращает
   INJECTION_BLOCKED без ticket_id; для HTTP — статус 422. В прямом create-ticket
   off-topic не запрещён: клиент уже явно запросил создание.

Цитаты Gmail/Outlook/Яндекс Почты, строки с `>` и HTML-блоки цитирования отделяются
до анализа намерения. Поддерживается новый текст перед цитатой, не ответы внутри неё.
Узкая благодарность без дополнительной просьбы получает фиксированный ответ без
модели и инструментов; её метрики нулевые и model=dialogue/acknowledgement.

## Контроль создания

Модель получает create-ticket с require_approval=always и только предлагает
аргументы. Поллер не одобряет автоматическое выполнение в Responses API:
выбирает первое предложение, проверяет его, задаёт собственные user_id/request_id
и делает один прямой MCP tools/call через SDK. Для list-my-tickets остаётся never.

request_id определяется входящим письмом. В YDB чтение и вставка выполняются
в одной SerializableReadWrite-транзакции: повтор получает исходный тикет,
не меняя его текст, дату или статус. Подтверждение формирует код из результата
инструмента, не из утверждения модели. Две реплики связываются с одним ID.

## Маскирование

Store.create_ticket маскирует tickets.text, Store.save_message — messages.text
обеих ролей. Текст также маскируется перед моделью и в исходящем ответе.

- Телефон: `+7 (***) ***-**-12` — остаются последние две цифры.
- Email в тексте: `[email]`.
- Номер карты 13–19 цифр: `****-****-****-****`.
- Явно обозначенный пароль/токен: `[SECRET]`.

Маскирование идемпотентно. user_id сохраняет адрес для связи записей и ответа;
это отдельное структурное поле, не текст обращения. Старые данные автоматически
не переписываются. Паспорт, пропуск и свободный почтовый адрес этот набор правил
полностью не распознаёт: это известное ограничение, не универсальный PII-детектор.

Код логирует имена действий, классы ошибок, маскированные поисковые запросы,
токены и время; полные письма, секреты и найденные фрагменты не логируются.

## Проверка и ограничения

```bash
python scripts/check_guardrails.py
python scripts/check_review_security.py
python scripts/check_qa_flow.py
```

Первая команда не пишет в YDB; остальные используют случайные тестовые записи
и удаляют их, SMTP подменён. Результаты и новые почтовые скрины —
[evidence/README.md](evidence/README.md). Деплой — [review-update.md](review-update.md).
Маски хранения подтверждены pii-storage-check.json, включая прямую запись в tickets.

GUARDRAIL_FAIL_OPEN=true оставлен по заданию: при сбое классификатора действует
regex, семантическая защита не гарантируется. false означает отказ при сбое.
Диагностический check_guardrails.py использует fail-closed, чтобы сбой модели
не дал ложного успеха. Проверка текстов не заменяет IAM и ACL сотрудников.

Cloud Logging недоступен в ограниченном режиме платформы: сообщение сохранено
в logging-unavailable.json. Отсутствие PII в фактических облачных логах не проверено.
Отдельные UI-фильтры токсичности/PII не подтверждены. Вызов content_filter
обрабатывается кодом, но включение специальных UI-настроек не заявляется.
