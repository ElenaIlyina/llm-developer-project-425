## Trusted и untrusted

Trusted: системный промпт из репозитория, определения MCP-инструментов,
параметризованные YQL-запросы, константное описание задачи и примеры классификатора.
Untrusted: тело письма, заголовки и адрес From, история переписки, текст и результаты
RAG, аргументы инструментов, сформированные моделью.

Внешний текст не вставляется в instructions. Текущее обращение передаётся как
JSON {sender_email, message} в пользовательском сообщении Responses API;
история тоже остаётся сообщениями, а RAG — результатами инструмента.
Адрес From используется для связи данных, но не является криптографически
подтверждённой идентичностью сотрудника. ИИ-проверка текста не заменяет ACL.

## Guardrail

1. Нормализация Unicode и regex обнаруживают явные ignore previous instructions,
   русские аналоги и разрушительные SQL-команды. Совпадение безусловно блокируется
   без обращения к модели, в лог пишется ALERT_INJECTION_BLOCKED.
2. Остальной текст после маскирования направляется в официальный few-shot
   Text Classification API на cls://<folder>/yandexgpt-lite/latest.
   Классы: safe / injection / off-topic. Task description и samples константны,
   входной текст передаётся отдельно в поле text.
3. email-poller проверяет письмо до вызова основного агента. Injection получает
   отказ, off-topic — предложение сформулировать рабочий вопрос. Сохраняются
   маскированные реплики, но агент и MCP не вызываются.
4. ydb-tickets независимо проверяет create-ticket перед записью. Injection
   возвращает {error: INJECTION_BLOCKED, blocked: true}; для HTTP статус 422.
   Даже прямой invoke не обходит эту проверку.
   При прямом запросе create-ticket off-topic допускается и логируется — вызывающий
   клиент уже явно запросил создание. В почтовом канале off-topic отклоняется.

GUARDRAIL_FAIL_OPEN=true соответствует подсказке задания: при недоступности
классификатора проверка деградирует до safe с GUARDRAIL_UNAVAILABLE в логах.
Regex при этом продолжает блокировать явные атаки. Для строгого отказа установите
GUARDRAIL_FAIL_OPEN=false у обеих функций. При fail-open семантическая защита
не гарантируется во время сбоя модели. Успешный health-check запускается
принудительно с fail-closed, чтобы недоступный классификатор не выдал ложный успех.

require_approval: never сохранён для MCP в соответствии с заданием. Согласие
пользователя на заявку проверяется консервативным фильтром почтового маршрута:
create-ticket доступен только при распознанной просьбе или согласии после
предложения. Успех формируется кодом из результата MCP. Прямой MCP-вызов
не использует почтовую проверку согласия; отдельного серверного ACL по сотрудникам нет. Guardrail проверяет содержание обращения, а не все возможные права
и бизнес-полномочия. RAG-документы считаются данными и не могут давать разрешение
на действия. Инструментов удаления данных агенту не предоставлено.

## PII на границе записи

Store.create_ticket маскирует tickets.text; Store.save_message маскирует
messages.text для обеих ролей. Маскирование также выполняется перед передачей
текста классификатору/агенту и перед ответом по почте.

- Российский телефон: +7 (***) ***-**-12, сохраняются последние две цифры.
- Email в тексте: [email].
- Числовая последовательность 13–19 цифр, похожая на номер карты: ****-****-****-****.
- Явно обозначенный пароль/токен: [SECRET].

Функция идемпотентна: повторное маскирование не меняет уже скрытые значения.
user_id остаётся адресом в структурном поле/ключе БД для поиска переписки;
это необходимое исключение из маскирования text, оно не выводится в логи.
UPDATE связи с ticket_id и UPDATE статуса из workflow не изменяют текст.
Уже существующие записи автоматически не переписываются.
Регулярные выражения не являются универсальным распознавателем всех видов PII.

В логах — action, label, метод проверки, класс ошибки, число токенов и время.
Сырые тексты, аргументы create-ticket, пароли и содержимое ошибок API не логируются.
Queries RAG проходят маскирование; фрагменты документов не пишутся в лог.

## Встроенная модерация AI Studio

По документации системное правило применяется по умолчанию к моделям Яндекса.
Пользовательские правила Preview настраиваются для инстансов модели, а не для
нашего inline-вызова UI-агента. Наша обработка распознаёт content_filter и
возвращает пользователю сообщение о модерации вместо технической ошибки.

Наличие отдельных настроек «токсичность + детектор PII» в UI из задания ещё
не подтверждено. Не заявляем их включёнными вручную. PII скрывается кодом
независимо от встроенной модерации. Для точного выполнения UI-пункта нужно
проверить доступные настройки инстанса и при необходимости уточнить требование;
не отключать штатное системное правило ради неподтверждённой настройки.

Повторите обычный RAG-вопрос, чтобы проверить регрессию после изменения контекста.

### Уточнение почтовой проверки PII

Первое чтение БД показало правильные маски в messages и отсутствие сырых
тестовых данных во всех прочитанных текстах. Модель сократила tickets.text
до «Тестовый принтер не печатает.», поэтому требование наличия всех масок
в этой краткой сводке было ложной предпосылкой проверки. В комплект сдачи включён итоговый результат pii-storage-check.json.
Проверка разделена: почтовая история должна содержать маски; граница записи
tickets проверяется отдельным прямым create-ticket с исходными тестовыми PII,
затем чтением через --boundary-ticket-id. Логи пока недоступны через CLI,
и их безопасность не считается подтверждённой.

### Ограничение платформы при просмотре логов
